# Isolate control identity from operational data

Follow the current phase-1 specification: CRMF owns user authentication in M1, not the legacy M0 Keycloak setup. Identity tables and the `citext` extension live in `auth`, operational tables in `core`; application roles own neither and cannot assume the migrator role. `crmf_auth` alone accesses identity data, while both application roles can only append to the audit log. The ordinary API and worker no longer connect as the migrator.

Role creation is a separate administrative bootstrap, not an implicit privilege escalation inside a domain migration. The tracked bootstrap contains disposable local credentials only and is rerunnable on existing `crmf-dev` volumes; Azure provisioning must supply separate credentials/managed identities and equivalent grants. Control migrations are forward-only because an automatic rollback must not erase identities or audit history.

Future QG audit reads need an explicitly scoped reader design; do not solve that requirement by granting the general core role read/update/delete access to audit history. Tenant provisioning and complete login/MFA enforcement remain subsequent M1 work. The second increment adds database-enforced single-tenant/realm grants and transactional session revocation, plus a session resolver that reloads persisted authorization. Identity-before-session lock ordering avoids reversal between grant mutations and session resolution. Keycloak stays as an unused legacy development dependency until the authentication cutover; no new endpoint authenticates through it.
